# Hookbox

Кроссплатформенный сервис интеграции на Python 3.11+: принимает вебхуки, проверяет Bearer-токен и права пользователя, выполняет заданные в YAML команды или HTTP-запросы. Работает в обычном процессе; для постоянного запуска предусмотрены примеры systemd и NSSM.

## Быстрый запуск

Linux:

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements-dev.txt
cp config.example.yaml config.yaml
export PYTHON_EXECUTABLE="$(pwd)/.venv/bin/python"
.venv/bin/python main.py --generate-token
```

Windows, PowerShell:

```powershell
py -3 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
Copy-Item config.example.yaml config.yaml
$env:PYTHON_EXECUTABLE = (Resolve-Path .\.venv\Scripts\python.exe).Path
.\.venv\Scripts\python.exe main.py --generate-token
```

Генератор выводит JSON с полями `token` и `sha256`. Сохраните токен у вызывающего клиента, а SHA-256 задайте в переменной окружения `WEBHOOK_TOKEN_SHA256`. Открытый токен не требуется серверу. Например:

```bash
export WEBHOOK_TOKEN_SHA256='<SHA-256 из вывода генератора>'
.venv/bin/python main.py --config config.yaml --check-config
.venv/bin/python main.py --config config.yaml
```

```powershell
$env:WEBHOOK_TOKEN_SHA256 = '<SHA-256 из вывода генератора>'
.\.venv\Scripts\python.exe main.py --config config.yaml --check-config
.\.venv\Scripts\python.exe main.py --config config.yaml
```

В другом терминале передайте токен, полученный при генерации:

```bash
curl http://127.0.0.1:8080/hooks/echo \
  -H 'Authorization: Bearer <токен>' \
  -H 'Content-Type: application/json' \
  --data '{"message":"hello"}'
```

```powershell
$headers = @{ Authorization = 'Bearer <токен>' }
Invoke-RestMethod http://127.0.0.1:8080/hooks/echo -Method Post `
  -Headers $headers -ContentType 'application/json' -Body '{"message":"hello"}'
```

Пример запускает `examples/echo_payload.py` и возвращает полученный JSON. Вебхук `forward` выключен: для использования укажите свой адрес и включите его. Токен из примера ограничен ролью `echo_runner`, поэтому для `forward` также потребуется расширить его роли или создать отдельный токен.

Для установки без инструментов тестирования используйте `requirements.txt`.

## Конфигурация

Файл содержит три секции: `general`, `webhook`, `security`. Полный пример находится в [config.example.yaml](config.example.yaml). Неизвестные поля, повторяющиеся YAML-ключи и некорректные ссылки на роли/пользователей/хуки считаются ошибками. Перед запуском можно проверить файл через `--check-config`.

В строковых значениях поддерживается `${NAME}` — подстановка переменной окружения при чтении YAML. Отсутствующая переменная останавливает запуск. Конфигурация читается один раз; после изменения требуется перезапуск. Рабочие каталоги команд и пути SSL-файлов вычисляются относительно каталога YAML. Аргументы команд и URL автоматически не дополняются данными входящего запроса.

### Сервер: `general`

| Поле | Назначение |
| --- | --- |
| `host`, `port` | Адрес прослушивания; по умолчанию `127.0.0.1:8080`. |
| `url` | Необязательный публичный URL для метаданных; не меняет адрес прослушивания и не включает HTTPS. |
| `ssl.certfile`, `ssl.keyfile` | Сертификат и ключ для HTTPS непосредственно в сервере; указываются вместе. |
| `log_level` | Уровень журналирования. |
| `max_body_bytes` | Предельный размер входящего тела; по умолчанию 1 МиБ. |
| `body_timeout_seconds` | Время ожидания входящего тела; по умолчанию 30 секунд. |
| `max_concurrent_requests` | Максимум одновременно выполняемых вебхуков на процесс; по умолчанию 8. |

При размещении за reverse proxy TLS можно завершать на нём, оставив сервер на loopback. Bearer-токен даёт доступ предъявителю, поэтому для передачи через сеть используйте HTTPS.

### Вебхуки: `webhook`

Ключ элемента — идентификатор вебхука, на который ссылаются роли. Поля элемента:

| Поле | Назначение |
| --- | --- |
| `path` | URL-путь; по умолчанию `/hooks/<идентификатор>`. |
| `methods` | Список разрешённых методов из `POST`, `PUT`, `PATCH`; по умолчанию `[POST]`. |
| `enabled` | Включён ли вебхук; по умолчанию `true`. |
| `expose_output` | Возвращать ли вывод команд и тела ответов внешних сервисов; по умолчанию `false`. В демонстрационном `echo` включён. |
| `actions` | Непустой список действий, выполняемых по порядку. |

Тело запроса должно быть JSON с `Content-Type: application/json` или `application/*+json`. Пустое тело передаётся действию как `null`. Команды и HTTP-запросы выполняются до ответа клиенту; при первой ошибке цепочка останавливается. Уже выполненные действия не откатываются, результаты предыдущих действий не подставляются в следующие.

Действие `command`:

```yaml
type: command
command: ['/usr/bin/bash', '/opt/scripts/deploy.sh']
cwd: /opt/scripts
env:
  DEPLOY_TARGET: staging
timeout_seconds: 60
stdin_from_payload: true
max_output_bytes: 65536
```

`command` — список исполняемого файла и отдельных аргументов. Автоматического запуска shell нет: если нужен Bash или PowerShell, его нужно указать явно, например `['powershell.exe', '-NoProfile', '-File', 'C:/scripts/deploy.ps1']`. JSON из вебхука передаётся в stdin, а не исполняется как команда. При `stdin_from_payload: false` stdin пуст. `cwd` задаёт рабочий каталог, `env` дополняет окружение процесса. Ненулевой код завершения означает ошибку. После завершения действия, в том числе по таймауту, сервис завершает оставшиеся дочерние процессы: фоновые задания внутри действия не поддерживаются. Для Windows используется Job Object, для Linux — группа процессов; выполняемые скрипты не должны отделять процессы в самостоятельные службы.

Действие `http`:

```yaml
type: http
url: https://internal.example/api/tasks
method: POST
headers:
  Authorization: 'Bearer ${DOWNSTREAM_TOKEN}'
forward_payload: true
timeout_seconds: 30
max_output_bytes: 65536
```

Для постоянного JSON-тела вместо `forward_payload: true` задайте `body`. Явное `body: null` передаёт JSON `null`; если `body` отсутствует и пересылка отключена, тело не отправляется. Допустимы методы `GET`, `POST`, `PUT`, `PATCH`, `DELETE`. Адрес, метод и заголовки задаются конфигурацией. Входящий `Authorization` не пересылается; исходящие credentials задаются отдельно. Проверка TLS включена, HTTP-перенаправления автоматически не выполняются. Любой статус вне `200–299` прерывает цепочку. Сервис запрашивает несжатый ответ (`Accept-Encoding: identity`); сжатые ответы отклоняются с `502`, чтобы ограничение памяти не зависело от распаковки. По истечении таймаута исходящий запрос отменяется. Если системный DNS-вызов ещё выполняется в рабочем потоке, возврат ошибки `504` может задержаться до завершения этого вызова; отменённый запрос после разрешения имени не возобновляется.

`max_output_bytes` ограничивает сохраняемый вывод действия: отдельно для stdout и stderr команды, а для HTTP — тело ответа. Обрезанный вывод отмечается в результате; некорректные UTF-8-последовательности заменяются символом замены. `expose_output` включайте только для хуков, чьи ответы разрешено видеть владельцам соответствующего токена. Команды исполняются с правами учётной записи службы; YAML должен быть доступен на запись только администратору сервиса.

### Права: `security`

```yaml
security:
  roles:
    deployers: [deploy]
    administrators: ['*']
  users:
    ci:
      roles: [deployers]
      enabled: true
  tokens:
    ci_main:
      user: ci
      sha256: '${CI_TOKEN_SHA256}'
      roles: [deployers]
      enabled: true
```

Роль содержит идентификаторы доступных хуков; `'*'` разрешает все хуки. Пользователь получает роли, токен привязан к одному пользователю. Если `tokens.<name>.roles` отсутствует, токен наследует роли пользователя; явно указанный список сужает их и не может добавлять чужие роли. Пустой список не даёт доступа к хукам. Отключение пользователя блокирует все его токены; отключение токена блокирует только его. Отдельного входа по паролю и выдачи сессий в этой версии нет.

## Эксплуатация

`GET /healthz` доступен без токена и проверяет, что HTTP-процесс отвечает; доступность внешних сервисов и исполняемых файлов он не проверяет. Для вызова вебхука требуется `Authorization: Bearer <токен>`.

Успешный вызов возвращает JSON с `status: ok`, идентификатором `webhook`, `request_id` и списком `results`. При ошибке действия ответ содержит `status: error`, `failed_action` (индекс с нуля), `error` с кодом и сообщением, а также результаты уже выполненных действий. `request_id` также передаётся в заголовке `X-Request-ID` и связывает выполнение с журналом сервиса.

| HTTP-статус | Значение |
| --- | --- |
| `200` | Все действия завершились успешно. |
| `400` / `413` / `415` | Некорректный JSON или заголовок длины / слишком большое тело / неподдерживаемый тип либо кодирование тела. |
| `408` | Истёк таймаут получения входящего тела. |
| `401` / `403` | Токен отсутствует или недействителен / токен не имеет доступа к хуку. |
| `404` / `405` | Путь отсутствует или хук выключен / метод не разрешён. |
| `503` | Достигнут лимит одновременно выполняемых хуков. |
| `502` / `504` | Действие завершилось ошибкой / истёк его таймаут. |
| `500` | Непредвиденная ошибка исполнения действия. |

Первая версия не содержит очереди, хранения истории, автоматических повторов и защиты от повторного выполнения. Повторный вызов вебхука повторно запускает действия. Если действие завершилось, а клиент не получил ответ из-за разрыва соединения, повтор клиентом также может выполнить действие ещё раз. Для операций с побочными эффектами предусматривайте идемпотентность в вызываемых скриптах или внешнем API. Параллельные запросы могут запускать один хук одновременно.

### Linux: systemd

Разместите проект в `/opt/hookbox`, создайте там виртуальное окружение и установите `requirements.txt`. Создайте отдельного системного пользователя `hookbox` с группой того же имени. Дайте ему доступ на чтение к проекту/конфигурации, исполнение к интерпретатору и необходимым скриптам, запись — к каталогам, где этого требуют действия.

Для примера создайте `/etc/hookbox.env` с реальными значениями:

```ini
PYTHON_EXECUTABLE=/opt/hookbox/.venv/bin/python
WEBHOOK_TOKEN_SHA256=<SHA-256 из вывода генератора>
```

Ограничьте доступ к этому файлу, например `root:root`, режим `600`. Укажите дополнительные переменные окружения, которые использует ваш YAML. Файл обязателен для приложенного unit; при отказе от env-подстановок соответствующую строку `EnvironmentFile` можно убрать.

Установите unit из [deploy/hookbox.service](deploy/hookbox.service):

```bash
sudo install -m 644 deploy/hookbox.service /etc/systemd/system/hookbox.service
sudo systemctl daemon-reload
sudo systemctl enable --now hookbox
sudo systemctl status hookbox
sudo journalctl -u hookbox -f
```

Пути, пользователя и лимит ожидания остановки (`TimeoutStopSec=120`) адаптируйте под установку и длительность цепочек действий. Unit перезапускает процесс при сбое и пишет логи в journal. Значение и применение `WorkingDirectory` и `EnvironmentFile` описаны в [systemd.exec](https://freedesktop.org/software/systemd/man/latest/systemd.exec.html).

### Windows: NSSM

Подготовьте проект, виртуальное окружение и `config.yaml`, установите NSSM. В PowerShell **от администратора** выполните:

```powershell
.\deploy\install-nssm.ps1 `
  -InstallDirectory 'C:\Services\hookbox' `
  -NssmPath 'C:\Tools\nssm\win64\nssm.exe' `
  -TokenSha256 '<SHA-256 из вывода генератора>'
```

Дополнительно поддерживаются `-ConfigPath`, `-PythonPath`, `-ServiceName`. Скрипт устанавливает службу, но не запускает её. Повторный вызов для существующей службы завершается ошибкой, сохраняя её настройки. При частичном сбое установки проверьте созданную службу перед повтором.

По умолчанию служба работает от `NT AUTHORITY\LocalService`. Предоставьте этой учётной записи чтение/исполнение каталога приложения и запись в `logs`; права на остальные ресурсы зависят от команд. При необходимости задайте отдельную сервисную учётную запись через настройки NSSM. `LocalService` не получает права администратора из-за запуска установщика от администратора.

```powershell
Start-Service hookbox
Get-Service hookbox
Get-Content 'C:\Services\hookbox\logs\stdout.log' -Wait
Stop-Service hookbox
```

Установщик задаёт автоматический старт, перезапуск после сбоя, файлы stdout/stderr с ротацией и ожидание штатного завершения до 120 секунд. В окружение службы записываются `PYTHON_EXECUTABLE` и `WEBHOOK_TOKEN_SHA256`; открытый токен туда не записывается. Дополнительные переменные добавляйте через NSSM, сохраняя уже заданные: `AppEnvironmentExtra` заменяет список при установке. Подробности настройки — [NSSM usage](https://nssm.cc/usage) и [NSSM commands](https://www.nssm.cc/commands).

## Разработка и регрессия

Правила работы зафиксированы в [AGENTS.md](AGENTS.md): каждое добавленное или изменённое поведение покрывается регрессионными тестами, после каждой итерации запускается **полный** набор. При сбоях вносятся исправления и повторяется полный прогон.

```bash
# Linux
.venv/bin/python -m pytest -q
```

```powershell
# Windows
.\.venv\Scripts\python.exe -m pytest -q
```

[CI](.github/workflows/tests.yml) настроен на полный прогон в Ubuntu и Windows с Python 3.11 и 3.14. Настройка матрицы сама по себе не означает, что прогон уже состоялся. Установка и управление настоящими службами требуют отдельной проверки на целевой машине.
